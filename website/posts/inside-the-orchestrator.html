Inside the orchestrator: how Michael plans a run

30 August 2026 Intelligent orchestration

Michael is the default orchestrator, and the interesting part is not that a model writes the plan — it is everything Relay does around that plan so a bad answer cannot break your project or strand a run.

Planning is read-only by construction

Every new run starts in a persisted planning state and launches Michael through the engine and model selected at startup. Planning runs in Claude plan mode or the Codex read-only sandbox, so the planning phase cannot modify the repository at all. That is a property of the mode the CLI is launched in, not a promise about model behaviour.

Michael's session also runs from the Hive workspace rather than your main checkout. Claude starts in restricted safe mode with its file tools confined to the Hive; Codex uses its workspace-write sandbox rooted in the Hive. Relay remains the sole owner of worker launch, worktrees, review, integration, verification, and cleanup.

What Michael receives, and what it must return

Michael is given the objective, the run mode, the available providers, and the eligible saved-agent roster. It returns a JSON plan of one to four tasks. Relay then validates every title, role, deliverable, provider, and profile assignment before creating any worktrees.

If the output is invalid, the planner is missing, or the planner process exits non-zero, Relay automatically produces a deterministic fallback plan instead of stranding the run. The planner transcript stays available in Console, and the monitor shows the plan source, the rationale, and any fallback error — so a fallback is visible rather than silent.

Blockers become routed messages, not dead ends

Workers can emit a bounded RELAY_BLOCKER report. Relay turns that into a blocked task plus a durable message in Michael's hive inbox and its messages.jsonl stream. Failed, blocked, or stopped runs expose an explicit Re-plan action that creates a fresh model-planned run without mutating historical results; the re-plan keeps a parent-run link and sends the prior blocker evidence to Michael, so replacement tasks address the failed approach instead of repeating it.

Actions cross a durable boundary

Michael can answer in the terminal or request a Monitor action through control/outbox/. Relay accepts only the documented version-1 action allowlist and validates every identifier, provider, strategy, decision, and concurrency value in the main process. Malformed, unknown, or out-of-bounds actions produce durable rejected receipts.

Each accepted action crosses a durable control/actions/ execution boundary before Relay mutates state. A completed receipt is reused rather than re-run, and an action left executing by a crash is quarantined and reported for inspection instead of being executed a second time. Control commands themselves stay immutable in control/inbox/; commands without a matching acknowledgment are replayed after a restart, without replacing their audit files.

Memory that Relay does not overwrite

memory.md is Michael's curated long-term memory, and Relay never replaces it. Human inputs, final run states, action outcomes, and recovery events are deduplicated into the append-only history.jsonl journal; Relay projects the latest 30 entries into context.md, and every fresh Michael session reads both files before accepting work. Renaming the orchestrator updates its identity and registry without moving its stable folder.

Closing the loop

After the workers finish, Michael runs in a read-only synthesis terminal and publishes one compact outcome; if the model is unavailable or its output is malformed, a deterministic summary is retained instead. Planning, blocker, synthesis, and task state are all projected into the hive board, inbox, message stream, and structured task ledger — which stays readable independently of the UI. Planner, worker, synthesis, and verification phases each stop after a bounded watchdog.
