Features

Six subsystems that make multi-agent work reviewable

Relay's value is not "more agents" — it is that every plan, worker, diff, decision, and failure is bounded, persisted, and scoped to one project on one machine.

01 · Orchestration

Intelligent orchestration lifecycle

Every run starts in a persisted planning state and ends with one compact synthesized outcome. Michael uses the Claude or Codex model you selected at startup.

  • Three run modes. Build assigns an implementation owner plus an independent reviewer; Split turns newline or semicolon-separated instructions into parallel workstreams; Audit asks each worker for an independent, evidence-backed investigation.
  • Read-only planning. Planning runs in Claude plan mode or the Codex read-only sandbox and cannot modify the repository.
  • Validated plans. Michael returns a one-to-four task JSON plan; Relay validates every title, role, deliverable, provider, and profile assignment before creating worktrees.
  • Never stranded. Invalid output, a missing planner, or a non-zero planner exit produces a deterministic fallback plan instead of a dead run.
  • Re-plan with history. Failed, blocked, or stopped runs expose an explicit Re-plan that links to the parent run and forwards prior blocker evidence, without mutating historical results.
  • Blocker routing. A worker can emit a bounded RELAY_BLOCKER report, which becomes a blocked task plus a durable message in Michael's hive inbox and the messages.jsonl stream.
  • Synthesis. After workers finish, Michael runs in a read-only synthesis terminal; a deterministic summary is retained if the model is unavailable or malformed.
02 · Isolation

Isolated Git worktrees

Concurrent agents need concurrent checkouts. Every task gets its own branch and directory, and your working tree stays untouched until integration.

  • Project-local storage. Managed worktrees live under <project>/.relay/worktrees/, matching the workflow Claude Code already uses.
  • Clean ignore handling. Relay adds /.relay/worktrees/ to the repository's local .git/info/exclude and leaves the tracked .gitignore alone.
  • Validated before Git. Worktree and branch names are checked first — a name such as ../escape is rejected before Git ever sees it.
  • Safe removal. Removal refuses dirty worktrees, branches with commits ahead of their base, and any worktree a live terminal is using.
  • Recovery-friendly. Removing a worktree leaves its Git branch intact; missing worktrees stay visible and can be forgotten without touching repository content.
  • Bounded Git. Relay's Git commands run without a shell, use argument arrays, disable repository hooks and terminal prompts, and have bounded output and execution time.

03 · Providers

Provider adapters: Claude Code + Codex CLI

Both CLIs sit behind one adapter contract covering discovery, worker launch, and read-only verification — so a run can mix them freely.

  • Discovery. Provider availability is detected on PATH, cached for ten seconds, and concurrent checks are de-duplicated to keep startup bounded.
  • Claude workers. Run in non-interactive edit-accepting mode inside their own worktree.
  • Codex workers. Run in a workspace-write sandbox with approvals disabled inside their own isolated checkout.
  • Orchestrator restraint. Michael's persistent CLI runs from the hive, not your checkout: Claude starts in restricted safe mode with file tools confined to the hive; Codex uses a workspace-write sandbox rooted in the hive.
  • Real terminals. node-pty sessions with xterm.js give live output, serialized input, bounded dimensions, and replay across tab switches and renderer reloads.
  • No command injection. Provider commands are fixed and resolved without a shell; model identifiers pass as bounded argument values, and renderer requests cannot inject CLI arguments.
  • Legible failures. Authentication, filesystem permission, usage-limit, network, and generic command failures are translated into distinct actionable errors.
04 · Safety

Safety boundaries

The renderer is a UI, not a privileged client. Filesystem, database, Git, PTY, and provider operations stay in the Electron main process behind typed IPC.

  • Project scoping. Every repository, worktree, run, task, and terminal request is authorized against the currently selected project.
  • What the renderer cannot do. Inspect another repository, operate on historical runs from another project, assume an internal terminal role, choose an arbitrary terminal directory, or inject provider CLI arguments.
  • Audited denials. Every denied boundary request is recorded as an app.safety.denied system event.
  • Path integrity. Relay refuses symlinked hive control directories and managed worktree storage that resolves outside the selected project.
  • Terminal placement. Worker terminals may start only in the selected checkout or a live Git-registered worktree.
  • Bounded runtime. Watchdog timeouts on planner, worker, synthesis, and verification phases; at most 12 live PTYs and 64 retained sessions; 1 MiB of retained output per session.
  • Electron hardening. Renderer permission requests are denied, unexpected top-level navigation is blocked, HTTPS links open externally, and a restrictive Content Security Policy applies.
  • Allowlisted actions. Michael can request a Monitor action, but Relay accepts only the documented version-1 allowlist and validates every identifier, provider, strategy, decision, and concurrency value in the main process.
05 · Durability

Persistence & recovery

Crashes and quits are normal events, not data loss. Runs, reviews, memory, and pending commands are all designed to be replayed exactly once.

  • SQLite state. Run and task state persists in SQLite; interrupted work is surfaced as blocked after restart rather than silently resumed.
  • Curated memory. memory.md is Michael's long-term memory and Relay never replaces it; identity files are refreshed by the harness.
  • Deduplicated journal. Human inputs, final run states, action outcomes, and recovery events append to history.jsonl; the latest 30 entries project into context.md, which every fresh session reads.
  • Exactly-once controls. Control commands are immutable in control/inbox/; anything without an acknowledgment in control/.done/ is replayed after restart, without replacing its audit files.
  • Durable action boundary. Each accepted action crosses control/actions/ before state mutates. Completed receipts are reused; an action left executing by a crash is quarantined and reported instead of run twice.
  • Non-destructive recovery. Automatic and manual recovery retain interrupted runs as blocked, refresh hive projections, drain recoverable actions, and preserve every worktree and branch.
  • Integration you control. Bounded per-file diffs change no Git state; every task must be explicitly accepted or rejected; accepted tasks are squashed onto the checked-out base in task order; integration refuses a dirty checkout or the wrong branch, and conflicts are reported by file and aborted cleanly.
06 · Reuse

Agent profiles & team templates

Stop re-describing your crew. Save the agents that work, save the team that ships, and load either before a run.

  • Profiles. A reusable agent stores a person name, animated DiceBear avatar seed, CLI provider, optional model, instructions, and enabled state.
  • Same CLI, many specialists. Multiple profiles may use one provider, so specialized workers run concurrently in separate worktrees.
  • Templates. A team template saves an objective, run mode, concurrency, and up to four agent profiles.
  • One command surface. Load a template or hand-pick saved agents before starting a run; the planner receives the eligible roster.
  • Persistent defaults. Run mode, agent concurrency, and preferred verifier persist inside the selected Harness Home.
  • Data stays data. Custom fields never become executable commands — provider commands remain fixed and model identifiers are bounded arguments passed without a shell.
  • Renaming is cheap. The orchestrator does not have to be called Michael; renaming updates identity and registry without moving its stable folder.
